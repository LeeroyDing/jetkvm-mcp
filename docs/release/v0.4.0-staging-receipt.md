## Reproducibility and verification results

- All four binaries were built twice and every pair passed `cmp`.
- `go version -m` on all four binaries reported `vcs=git`, revision
  `8d2b56445e06c88ecbf95f8f4b6ce02131a67ed1`, time
  `2026-08-15T19:52:13Z`, and `vcs.modified=false`.
- Gitleaks v8.24.3 found no leaks in the staged payload tree or in printable
  strings extracted from all four binaries. The workflow's explicit canary
  search also found no matches.
- All four archives were produced twice with GNU tar/gzip and every pair
  passed `cmp`.
- `sha256sum --check SHA256SUMS` passed for all five listed payloads.
- The extracted linux/amd64 binary reported JSON version `0.4.0` and commit
  `8d2b56445e06c88ecbf95f8f4b6ce02131a67ed1`; its Go build metadata again
  reported the expected revision and `vcs.modified=false`.
- The output envelope contained exactly `BUILDINFO`, `SHA256SUMS`, and the four
  target archives—six files total.
- A read-only download of the already-published `v0.4.0` assets produced the
  same six SHA-256 digests as this local bundle. It was used only for byte
  identity evidence; no release operation was performed.

The first packaging probe inherited the host's restrictive `077` umask. Its
extracted payload bytes were identical, but `LICENSE` and `README.md` had mode
`0600` rather than the Actions runner's `0644`, which correctly changed the
archive hashes. That probe was discarded. The recorded build set `umask 022`,
then repeated the complete two-build, hygiene, two-archive, checksum, and
metadata validation pipeline. This is why the umask is explicit in the
runbook rather than an unstated environmental assumption.
